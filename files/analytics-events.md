# Аналитика: события и метрики

Документ 4. Спека для разработки и для настройки дашборда.
Покрывает метрики из `onboarding-brief.md` (часть 7) и `day1-14-and-goals.md` (часть 5).

---

## Соглашения

```
Имена событий:     snake_case, глагол в прошедшем или существительное
Имена свойств:     snake_case
Время:             UTC ISO-8601 + отдельно local_hour (0–23) в свойствах
Идентификация:     anonymous_id до регистрации, user_id после, склейка через alias
```

**Свойства, отправляемые с каждым событием (super properties):**

| Свойство | Тип | Пример |
|---|---|---|
| `day_since_install` | int | 11 |
| `platform` | string | ios / android |
| `app_version` | string | 1.0.3 |
| `local_hour` | int | 22 |
| `is_subscriber` | bool | false |
| `weak_link` | string | movement |
| `budget_minutes` | int | 15 |
| `stopfactor_type` | string | category / system |

`weak_link`, `budget_minutes`, `stopfactor_type` появляются после онбординга — до него отсутствуют.

**Чего не собираем.** Тексты, которые пишет пользователь: своя задача, формулировки цели, препятствие. Ни в свойствах, ни в логах. Отправляем только `length` и `category`. Эти поля — самое личное, что есть в приложении, и в аналитике им делать нечего.

Событие `custom_task_blocked` с группой `self_harm` **не идёт в общий поток аналитики** и не попадает на дашборд. Оно нужно только для одного: убедиться, что экран с контактами поддержки показывается и не падает. Логируем факт показа, без user_id и без контекста.

## Метрика `grace_day_return`

Главная метрика всей стратегии. Считается так:

```
grace_day_return =
    пользователи с core_completed в течение 48 часов после grace_day_used
    ─────────────────────────────────────────────────────────────────────
    все пользователи с grace_day_used

Целевое значение: ≥ 85%
Окно: 48 часов, не 24 — человек мог пропустить по объективной причине
```

**Как читать результат:**

| Значение | Что означает | Что делать |
|---|---|---|
| ≥ 85% | механика считывается как прощение | ничего |
| 70–85% | текст экрана не убеждает | переписать экран дня 11, механику не трогать |
| < 70% | пользователь всё равно воспринимает это как провал | проверить, не показываем ли где-то рядом счётчик потерь |

**Важно:** при просадке метрики первым делом правится **текст**, а не механика. Механика опирается на Lally 2010 и является позиционированием — отказ от неё обнуляет весь блок 3 онбординга.

**Контрольная разбивка.** Сравниваем D14 и D30 у трёх групп:
- использовали прощённый день,
- пропустили дни, но прощённых не было (когорта до релиза механики),
- не пропускали вообще.

Если у первой группы D30 не отличается от третьей — гипотеза подтверждена, и это стоит вынести в маркетинг.

# 4. Пересчёт и итоги

| Событие | Когда | Свойства |
|---|---|---|
| `recalc_shown` | экран дня 7 | шесть значений до и после, `categories_up`, `categories_down` |
| `recalc_dismissed` | закрыт | `ms_on_screen` |
| `day14_summary_shown` | итог двух недель | `core_adherence_14d`, `grace_used`, `misses` |
| `tier_offered` | предложен следующий тир | `category`, `from_tier`, `adherence_14d` |
| `tier_accepted` | взял следующий | `category`, `to_tier` |
| `tier_postponed` | «остаться ещё на неделю» | `category`, `tier` |

**Сторожевая проверка на `recalc_shown`.** Если `categories_down = 0` больше чем у 20% пользователей — расчёт настроен неправильно. По устройству метода что-то почти всегда должно падать: анкета оптимистичнее реальности. Панель, где всё растёт, недостоверна, и пользователь это чувствует, даже если не формулирует.

# 8. Источники и метод

| Событие | Когда | Свойства |
|---|---|---|
| `source_link_tapped` | тап по DOI | `doi`, `context` onboarding/task/method |
| `task_why_tapped` | тап по иконке «i» | `task_id`, `doi_present` bool |
| `method_screen_opened` | открыт раздел «Метод» | `entry_point` |

**Гипотеза, которую эти события проверяют.** Доля тапающих по ссылкам мала — ожидаем 2–5%. Но у этой группы D30 и конверсия должны быть заметно выше средних. Если разницы нет — проверяемость не работает как УТП на этой аудитории, и позиционирование надо пересобирать вокруг чего-то другого (скорее всего, вокруг прощённых дней — они понятнее без объяснений).

Проверять на первой тысяче пользователей, не раньше: на меньшей выборке 3% — это 30 человек, и любая разница будет шумом.

# 10. Дашборды

**Дашборд 1 — Воронка онбординга.** Пошагово от `onb_start` до `onb_complete`, с разбивкой по `platform`. Отдельным виджетом — распределение `ms_spent` по вопросам: вопрос, на котором люди зависают дольше 15 секунд, сформулирован плохо.

**Дашборд 2 — Первые 14 дней.** Когортная сетка удержания по дням, вертикальные отсечки на днях 3, 7, 11, 14. Рядом — `core_adherence` по дням.

**Дашборд 3 — Прощённые дни.** `grace_day_return` как главное число. Под ним — сравнение D14/D30 трёх групп. Отдельно `downgrade_accepted / downgrade_offered`: если ниже 40%, предложение спуститься воспринимается как обвинение, и текст надо смягчать.

**Дашборд 4 — Контент.** Топ и антитоп задач по `completed / shown`. Микрозадача с конверсией ниже 30% выводится из ротации и переписывается. Это единственный дашборд, который смотрит копирайтер, а не продакт.

## Что настроить в первую очередь

Порядок по убыванию ценности, если ресурс ограничен:

1. `grace_day_used` + `core_completed` — без них не считается главная метрика.
2. Воронка онбординга целиком — она даёт больше всего материала для правок в первый месяц.
3. `recalc_shown` со сторожевой проверкой `categories_down`.
4. `custom_task_blocked` — не для аналитики, а чтобы убедиться, что фильтр вообще срабатывает в проде.
5. Всё остальное.
